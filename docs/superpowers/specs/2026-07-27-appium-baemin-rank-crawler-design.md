# Appium 기반 배민 카테고리 순위 실측 크롤러 — 설계서

- 날짜: 2026-07-27
- 작성 배경: `광고 순위 모니터링` 화면은 지금까지 전부 Mock 데이터다. 실제로 이런
  자동 수집이 가능한지 검증하고, 과제(교육 과정)에서 "실제로 테스트해봤다"는
  증빙자료를 만들기 위한 별도 도구를 만든다.
- 메인 프로젝트(`backend/`, `frontend/`, `schema.sql`)와는 **완전히 분리된
  독립 스크립트**다. 크롤링이 안정적으로 검증되면 그 결과(CSV)를 메인
  프로젝트의 DB/API에 연결하는 것은 이번 스펙 범위 밖이며, 다음 단계로 남긴다.

## 목적

배달의민족 앱에서, 내 가게의 실제 위치를 기준으로 특정 카테고리(예: 치킨)
목록에서 내 가게가 몇 번째로 노출되는지, 그리고 가게에서 1/2/3/4km 떨어진
지점에서는 순위가 어떻게 달라지는지를 실제로 측정한다.

## 범위와 원칙 (반드시 지킬 것)

- **개인적·1회성 테스트** 목적이다. 지속적인 프로덕션 크롤링(상시 자동 수집
  서비스)이 아니다.
- 배달의민족은 **로그인 없이 가게 목록을 열람**할 수 있다 — 계정 자격증명,
  세션, 로그인 자동화는 이 스크립트의 범위에 없다.
- 메인 데모 프로젝트(`CLAUDE.md`가 규정하는 "Mock만 사용" 원칙)와는 별개의
  독립 폴더(`crawler/`)에 존재하며, 메인 프로젝트의 백엔드·프론트엔드
  코드를 수정하지 않는다.
- 실제 배민 앱을 대상으로 하는 만큼, 짧은 1회성 실행에 그치고 반복적인
  상시 실행이나 다중 계정/다중 기기를 이용한 대규모 수집으로 확장하지
  않는다.

## 핵심 리스크와 검증 우선순위

가장 큰 불확실성은 "배민 앱의 카테고리 리스트가 Appium의 accessibility
tree(`driver.page_source`)로 읽히는가"이다. 이게 안 되면 파싱 전략 전체가
바뀐다. 그래서 본 구현은 **이 가정을 가장 먼저 검증하는 스파이크 태스크로
시작**한다 (구현 계획의 최우선 순위).

### 화면 파싱 방식 — 2가지 접근법

1. **Accessibility Tree 파싱 (1차 시도)** — `driver.page_source`로 얻은
   XML에서 가게명 텍스트 노드와 "광고" 배지 유무를 직접 읽는다. 빠르고
   정확하지만, 리스트가 커스텀 렌더링(예: 통짜 캔버스)돼 있으면 텍스트가
   트리에 노출되지 않을 수 있다.
2. **스크린샷 + OCR (대안)** — 매 스크롤마다 스크린샷을 찍고 OCR(Tesseract)로
   텍스트를 추출한다. 1번이 실패할 때만 전환한다. 느리고 노이즈가 많아
   "광고 배지" 인식이 더 어렵다.

1번으로 시작하고, 검증 스파이크에서 실패하면 2번으로 전환한다.

## 실행 환경

- macOS 호스트, **Android 에뮬레이터**(Android Studio AVD)를 Appium이 조작한다.
  실기기는 쓰지 않는다.
- Android Studio·SDK·Appium 전부 새로 설치해야 한다 (현재 Xcode만 설치돼
  있음 — iOS 시뮬레이터는 이번 스코프에 없다).
- 에뮬레이터의 GPS는 `adb emu geo fix <경도> <위도>` 명령으로 즉시 변경한다
  (실기기의 Mock Location 앱 설정보다 훨씬 간단).
- Appium 클라이언트는 **Python**(`Appium-Python-Client`)으로 작성한다 —
  메인 프로젝트 백엔드가 Python이라 추후 연동 시 코드 재사용이 쉽다.
- 배민 앱은 **Google Play가 포함된 에뮬레이터 이미지**를 써서 Play
  스토어에서 직접 설치한다 (APK 사이드로드는 하지 않는다). 앱의 Android
  패키지명(예: `com.sampleapp.baemin` 형태 — 정확한 값은 설치 후
  `adb shell pm list packages`로 확인)은 구현 첫 단계에서 확인해
  `config.py` 상수로 넣는다.
- `CATEGORY_LABEL`(카테고리 탭 문구)과 `STORE_DISPLAY_NAME`(가게 표시명)은
  **실제 앱 화면에 보이는 문구와 정확히 일치**해야 한다. 이 값들은 스크립트가
  추측하지 않는다 — 사장님이 실제 앱을 한 번 열어서 정확한 문구를 확인한
  뒤 `.env`에 입력하는 수동 준비 단계다.

## 아키텍처 (파일 구조)

메인 프로젝트와 형제 위치인 저장소 루트의 `crawler/` 폴더:

```
crawler/
├── requirements.txt        # Appium-Python-Client, requests, python-dotenv
├── .env.example            # KAKAO_REST_API_KEY, STORE_ADDRESS, STORE_DISPLAY_NAME, CATEGORY_LABEL
├── config.py               # .env 로드 + 반경 리스트 [1,2,3,4] km 상수
├── geocode.py              # 주소 문자열 → (위도, 경도). 카카오 로컬 API 호출
├── geo_sampling.py         # 기준좌표 + 반경 리스트 → 반경별 좌표 목록 (순수 함수)
├── appium_driver.py        # Appium 세션 시작/종료, adb geo fix 래퍼
├── baemin_navigator.py     # 앱 실행 → 카테고리 탭 이동 → 스크롤하며 page_source 누적 수집
├── rank_finder.py          # 누적 XML에서 항목 순서·광고 배지 파싱, 순위 판별 (순수 함수)
├── run_crawl.py            # 메인 실행 스크립트 (5개 지점 순회, 파일 출력)
└── output/
    ├── screenshots/{ISO시각}_{반경}km_{방위각}deg.png
    └── results.csv
```

각 모듈의 책임은 하나씩이다: `geocode.py`는 주소→좌표 변환만, `geo_sampling.py`는
좌표 계산만, `rank_finder.py`는 XML 파싱·순위 판별만 한다. 이 셋은 네트워크나
Appium 세션에 의존하지 않는 순수 함수로 만들어 개별적으로 테스트 가능하게 한다.

## 데이터 흐름

1. `run_crawl.py`가 `.env`에서 `STORE_ADDRESS`, `STORE_DISPLAY_NAME`,
   `CATEGORY_LABEL`을 읽는다.
2. `geocode.py`가 카카오 로컬 API로 주소를 기준 좌표(위도, 경도) 1개로
   변환한다. (카카오 개발자 계정에서 REST API 키를 사장님이 직접 발급받아
   `.env`에 넣는다 — 이 프로젝트가 대신 발급하지 않는다.)
3. `geo_sampling.py`가 반경 1/2/3/4km마다 0~360도 중 랜덤 방위각을 뽑아
   목적지 좌표를 계산한다(구면 삼각법 destination-point 공식). 기준점 포함
   총 5개 지점이 만들어진다.
4. 5개 지점을 순서대로 처리한다:
   a. `appium_driver.py`가 `adb emu geo fix`로 에뮬레이터 위치를 이동시킨다.
   b. `baemin_navigator.py`가 앱을 강제 종료 후 재실행(위치 갱신 반영) →
      카테고리 탭에서 `CATEGORY_LABEL`과 일치하는 탭을 탭한다.
   c. 리스트를 스크롤하면서 매번 `page_source`를 누적 수집한다.
   d. `rank_finder.py`가 누적된 XML에서 항목들을 순서대로 파싱하고, 각
      항목이 광고 배지를 가졌는지 표시하며, `STORE_DISPLAY_NAME`과 일치하는
      항목의 1-based 순번을 계산한다.
   e. 가게를 찾은 시점(또는 최대 스크롤 횟수 도달 시점)에 전체 화면
      스크린샷을 저장한다.
   f. CSV에 한 줄 추가: 시각, 반경(km), 방위각(도), 위도, 경도, 카테고리,
      순위(또는 `NOT_FOUND`), 스캔한 총 항목 수, 순위 위에 있는 광고 개수,
      스크린샷 경로.
5. 5개 지점이 모두 끝나면 콘솔에 요약 테이블을 출력한다.

## 순위의 정의

화면에 보이는 **전체 노출 순서 그대로** 센다. 배민 기본 정렬(추천순)은 광고
가게와 일반 가게가 섞여서 나오는데, 이 뒤섞인 순서 그대로가 실제 사장님이
확인하는 "체감 순위"이기 때문이다. 단, 각 항목이 광고인지 여부는 별도
컬럼(`is_ad`)으로 함께 기록해서, 나중에 "광고 제외 순수 순위"로 재계산할
수 있는 여지를 남긴다.

## 에러 처리

- **가게를 못 찾음**: 최대 스크롤 횟수(기본 30회) 도달 시 `NOT_FOUND`로
  기록하고 다음 지점으로 넘어간다. 전체 실행이 중단되지 않는다.
- **accessibility tree가 비어 있음**: 핵심 리스크가 현실화된 경우다.
  `PARSE_ERROR`로 기록하고, 원인 분석용으로 원본 `page_source` XML을
  `output/debug/`에 저장한 뒤 다음 지점으로 넘어간다.
- **지오코딩 API 실패**(키 누락, 주소 불명확 등): 첫 단계에서 즉시 중단하고
  명확한 에러 메시지를 출력한다 (지점 순회를 시작하기 전에 좌표가 있어야
  하므로 이 실패는 복구 불가능한 실패로 취급한다).
- **Appium 서버/에뮬레이터 연결 실패**: 실행 시작 전 헬스체크 단계에서
  확인하고, 실패 시 무엇을 확인해야 하는지(에뮬레이터 실행 여부, Appium
  서버 기동 여부) 안내 메시지와 함께 중단한다.

## 테스트

- `geo_sampling.py`: 알려진 기준좌표+반경+방위각 조합에 대해 계산된 좌표가
  기대값과 오차범위 내로 일치하는지 pytest로 검증한다 (haversine 역계산
  공식의 순수 단위 테스트).
- `rank_finder.py`: 실제 배민 앱에서 얻은 `page_source` XML 샘플을
  fixture로 저장해두고, 그 안에서 항목 파싱·광고 배지 인식·목표 가게
  순번 계산이 올바른지 pytest로 검증한다. (fixture는 검증 스파이크
  단계에서 실제로 한 번 앱을 열어 수집한다.)
- 앱 조작 자체(`appium_driver.py`, `baemin_navigator.py`)는 성격상 자동화
  테스트 대상이 아니다 — 실제 첫 실행이 곧 통합 테스트다.

## 산출물 (이번 스펙의 완료 기준)

- 카테고리 1개, 지점 5개(가게+반경4개)에 대해 스크린샷 5장 + `results.csv`
  1개가 생성된다.
- CSV에는 각 지점의 순위(또는 NOT_FOUND/PARSE_ERROR)와 광고 개수가 기록돼
  있어 "실제로 테스트했다"는 증빙이 된다.

## 다음 단계 (이번 스펙 범위 밖)

- 크롤링이 안정적으로 검증되면, `results.csv`를 메인 프로젝트의
  `ad_rank_snapshots`류 테이블/API에 연결하는 것을 별도 스펙으로 다룬다.
- 여러 카테고리·여러 매장으로 확장하는 것도 이번 스펙 범위 밖이다.
