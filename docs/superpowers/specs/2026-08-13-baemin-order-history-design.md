# 배민 주문내역(개별 주문) 실데이터 연동 — 설계

날짜: 2026-08-13
관련 결정: CLAUDE.md "방향 전환" 로드맵 3번의 연장선. 2026-08-11 매출·입금·
재주문율 설계 문서의 "범위 밖" 절에 "주문내역(개별 주문을 화면에 나열하는
페이지) 실데이터 연동은 별도 다음 단계로 미룬다"고 명시돼 있었다 — 이번이
그 다음 단계다. 대시보드/매출/입금 카드에 이어 "주문내역" 화면도 배민
실데이터로 교체하고, 대시보드 상단에 남아있던 낡은 "(Mock 데이터)" 라벨도
제거한다(2026-08-13, 이미 커밋 `bf00999`로 반영 완료 — 이 문서 범위 밖).

## 배경 / 목적

`주문내역`(`/orders`) 화면은 지금 `orders` 테이블을 그대로 보여주는데, 이
테이블은 `seed.sql`이 만든 랜덤 Mock 500건뿐이다. 배민은 이미 "데이터
동기화"가 주문내역 화면(`GET /v4/orders`)을 스크래핑하고 있지만
(`fetch_current_month_orders`), 지금은 그 결과를 날짜별 매출 합계로만
쓰고(`map_orders_to_daily_sales`) 개별 주문 행은 버린다. 이번 작업은 그
버려지는 개별 주문 데이터를 `orders` 테이블에 실제로 저장한다.

## 조사 과정에서 확인된 사실 (중요)

`fetch_current_month_orders`가 이미 캡처하는 `GET /v4/orders` 원본 응답을
실 계정으로 직접 열어봤다(2026-08-13, 227건 확인):

- `contents[].order`에 필요한 필드가 전부 이미 있다: `orderNumber`,
  `orderDateTime`("2026-08-13T02:19:37" 형식), `payAmount`, `itemsSummary`
  (예: "[양념조절가능]숯불양념바베큐치킨" — 메뉴 요약 문자열이 배민이 이미
  만들어 줌), `deliveryType`, `status`, `shopNumber`. `orders` 테이블
  스키마(주문번호/주문시각/주문메뉴/주문유형/주문금액)와 스키마 변경 없이
  그대로 맞아떨어진다.
- `deliveryType`은 실측 227건 전부에서 정확히 두 값만 나왔다:
  `DELIVERY`(223건), `TAKEOUT`(4건) — `orders.order_type`의 CHECK
  제약(`'delivery'`, `'takeout'`)과 1:1로 정확히 대응한다. 알려지지 않은
  세 번째 값이 나올 가능성에 대비해 매핑되지 않는 값은 하드 에러 대신
  그 주문 하나만 건너뛰고 로그를 남기는 방어적 처리를 한다(전체 동기화를
  막지 않기 위해 — 이 저장소의 기존 "한 항목 실패가 전체를 막지 않는다"
  원칙과 동일).
- `status`는 227건 전부 `"CLOSED"`였다 — 주문내역 화면 자체가 완료된
  주문만 보여주는 것으로 보인다(진행 중인 주문은 다른 화면에 있을 것으로
  추정, 이번 범위에서는 다루지 않는다).
- `order.orderNumber`는 최대 12자리 정도의 영숫자(예:
  "T2FE000020VQ")로, `orders.order_no VARCHAR(30) UNIQUE`에 문제없이
  들어간다.
- `shopNumbers` 쿼리 파라미터가 빈 채로 나가 계정에 연결된 모든 브랜드의
  주문을 한 번의 조회로 함께 반환한다(기존 `fetch_current_month_orders`
  문서화된 동작과 동일 — 브랜드별로 반복 호출할 필요 없음).

## 스코프 결정 1: 요기요/쿠팡이츠는 목록에서 제외

대시보드 매출/입금/재주문율 카드와 동일한 이유("실데이터와 Mock을 섞으면
숫자가 왜곡된다")로, 주문내역 목록도 **배민만** 보여주기로 결정했다.
`GET /orders` 응답 자체를 배민으로 필터링하지는 않는다(`platform_id` 쿼리
파라미터가 이미 있어 원한다면 다른 플랫폼도 조회 가능하게 API 자체는
유연하게 남긴다) — 프론트 `주문내역` 화면만 기본적으로 배민
`platform_id`로 필터링해서 요청한다. `orders` 테이블 자체에서 요기요/
쿠팡이츠 Mock 행을 삭제하지는 않는다(다른 화면·기능이 참조할 수도 있고,
이번 결정은 "주문내역 화면에 무엇을 보여줄지"이지 "요기요/쿠팡이츠 데이터를
지운다"가 아니다).

## 스코프 결정 2: 증분 동기화 (매번 3개월을 다시 긁지 않는다)

정산 상세와 달리 주문내역은 개별 주문 하나하나를 페이지네이션으로 긁어야
해서(실측: 진행 중인 이번 달 하나만 227건 — 3개월 전체라면 페이지네이션
클릭이 수십~수백 번 필요할 수 있다) 매번 넓은 기간을 다시 긁으면 "데이터
동기화" 전체 소요 시간이 크게 늘어난다. 그래서 아래처럼 상태 기반 증분
방식으로 설계했다:

- 동기화 시작 시 `orders` 테이블에서 이 매장·배민 플랫폼의 가장 최근
  `ordered_at`(`MAX(ordered_at)`)을 조회한다.
- **없으면**(최초 실행, 또는 아래 "기존 Mock 정리" 이후): 이번 달 포함
  최근 3개월을 백필한다(이 세션의 다른 실데이터 기능들과 동일한 폭) —
  한 번만 감수하는 비용이라 시간이 오래 걸려도 괜찮다고 결정했다
  (2026-08-13).
- **있으면**: `MAX(ordered_at) − 2일`부터 오늘까지만 다시 조회한다. 2일
  여유를 두는 이유는 주문 상태가 동기화 시점 이후에 바뀔 수 있어서다(예:
  방금 완료돼 `status=CLOSED`로 막 반영된 주문이 지난 동기화 시점엔 아직
  이 화면에 안 잡혔을 수 있음). `order_no` 기준 upsert라 겹치는 기간을
  다시 긁어도 중복 저장되지 않는다.
- 이 판단은 매장 단위(계정 전체, 브랜드별 아님)로 한다 — `fetch_current_
  month_orders`가 애초에 브랜드 구분 없이 계정 전체를 한 번에 반환하기
  때문에 브랜드별로 다른 커서를 둘 이유가 없다.

## 스코프 결정 3: 기존 Mock 주문 500건 정리는 일회성 작업

"매 동기화마다 배민 행을 지우고 다시 채우는" 방식(정산 입금이 쓰는 리셋
패턴)은 위 증분 로직과 충돌한다 — 증분 동기화는 기존 행을 신뢰하고 그
위에 새 행만 추가하는 게 핵심이기 때문에, 매번 지우면 증분의 의미가
없어진다. 그래서 `seed.sql`이 만든 배민 Mock 500건 정리는 **이 기능을
배포할 때 한 번만 실행하는 별도 SQL**(`DELETE FROM orders WHERE
platform_id = (배민 id)`)로 처리한다 — 이번 세션의 로컬 검증
과정에서와 동일하게, 실제 배포 시점에도 이 문서에 정확히 남겨진 절차를
그대로 한 번 실행한다. 이후로는 위 "없으면 3개월 백필" 분기가 자연스럽게
같은 결과를 만든다(Mock을 지운 직후엔 `MAX(ordered_at)`이 없으므로 자동
으로 깊은 백필이 시작된다) — 별도의 "이게 첫 동기화인지" 플래그를 두지
않아도 된다.

## API 응답 매핑

`GET /v4/orders` 응답의 `contents[].order.{orderNumber, orderDateTime,
payAmount, itemsSummary, deliveryType}`를 아래처럼 매핑한다:

```
order_no     = orderNumber
ordered_at   = orderDateTime (ISO 8601, 타임존 없는 "YYYY-MM-DDTHH:MM:SS" —
               배민 서버 로컬시간으로 그대로 저장, 기존 daily_settlements/
               repurchase_metrics의 날짜 처리와 동일하게 별도 타임존 변환
               없음)
menu_summary = itemsSummary (최대 200자, orders.menu_summary VARCHAR(200)
               제약 — 넘으면 잘라서 저장)
order_type   = deliveryType == "DELIVERY" → "delivery"
               deliveryType == "TAKEOUT"  → "takeout"
               그 외 값                    → 그 주문 하나만 건너뜀(로그)
amount       = payAmount
platform_id  = 배민 platform_id (고정)
store_id     = 동기화 대상 매장
```

## 동기화 흐름 (기존 "데이터 동기화"에 통합)

새 엔드포인트를 만들지 않는다. 기존 `fetch_current_month_orders`를
`fetch_orders(page, start_date, end_date) -> list[dict]`로 일반화한다(내부
스크래핑 로직은 그대로, 날짜 범위만 인자로 받도록 시그니처 변경) —
`_run_sync`의 기존 "이번 달 매출 보완" 호출도 이 함수를 그대로 쓰되
현재처럼 이번 달 1일~오늘 범위를 넘기고, 새로 추가되는 "개별 주문 저장"
호출은 위 증분 로직이 계산한 범위를 넘긴다. 두 호출은 서로 다른 목적
(날짜별 매출 합계 vs 개별 주문 행 저장)이라 각자 독립적인 try/except로
감싸 실패를 격리한다(기존 "일부 실패해도 나머지는 계속" 원칙).

1. (기존, 변경 없음) 이번 달 매출 보완: `fetch_orders(page, 이번달 1일,
   오늘)` → `map_orders_to_daily_sales` → `daily_settlements` upsert.
2. (신규) 개별 주문 저장: `MAX(ordered_at)` 조회 → 범위 결정(위 스코프
   결정 2) → `fetch_orders(page, 범위 시작일, 오늘)` → 새 순수 함수
   `map_order_rows(order_contents) -> list[dict]`(주문 하나당 위 매핑
   딕셔너리 하나, 매핑 안 되는 `deliveryType`은 건너뜀) → 새 upsert 함수
   `upsert_order(db, store_id, platform_id, ...) -> None`(`order_no` 기준,
   기존 upsert들과 동일한 select-then-insert-with-flush 패턴)로 하나씩
   반영.

## 에러 처리

| 상황 | 처리 |
|---|---|
| 개별 주문 저장 전체 실패(예: 스크래핑 자체가 안 됨) | job은 `success` 유지(다른 소스가 성공했다면), `error_message`에 "주문내역 동기화 실패" 추가 — 기존 "이번 달 매출 보완"은 별도 호출이라 영향 없음 |
| 특정 주문의 `deliveryType`이 알려지지 않은 값 | 그 주문 하나만 건너뛰고 나머지는 계속 저장 — 하드 에러 아님 |
| `menu_summary`가 200자 초과 | 잘라서 저장(하드 에러 아님) |
| `MAX(ordered_at)` 조회 자체는 되는데 이후 fetch가 실패 | 기존 데이터는 그대로 남고, 다음 동기화 때 같은 커서로 다시 시도됨(자연 재시도) |

## 프론트 변경

`frontend/src/app/(app)/sales/orders/page.tsx`:
- `GET /orders?store_id=...` 호출에 배민 `platform_id`를 추가해서 배민
  주문만 요청한다(기존 대시보드가 `baemin_id`를 조회하는 것과 동일한
  패턴, `GET /platforms`에서 `code === "baemin"`인 항목의 `id` 사용).
- 부제 문구 "최근 60일 주문 내역입니다."를 "최근 30일 주문 내역입니다."로
  바꾼다 — 증분 동기화 커서와 무관하게, 화면이 실제로 기대할 수 있는
  최소 보장 폭(최초 배포 시 3개월 백필되지만, 그 이후로도 계속 3개월치가
  DB에 남아있다는 보장은 없다 — 증분 로직은 "새 데이터를 계속 추가"만
  하지 "오래된 데이터를 지우지" 않으므로 실제로는 최초 백필 이후 계속
  누적된다. 문구는 보수적으로 "최근 30일"로 통일해서 실제 관찰 가능한
  최소 범위만 약속한다).

## 테스트 계획

- **backend (pytest)**: `map_order_rows`를 순수 함수로 분리해 실제로
  캡처한 응답 형태(DELIVERY/TAKEOUT 두 케이스, 매핑 안 되는 제3의
  `deliveryType` 값 하나)를 fixture로 박아 단위 테스트. `upsert_order`는
  신규 삽입/기존 갱신(order_no 충돌 시 덮어쓰기)을 테스트. 증분 범위 계산
  로직(`MAX(ordered_at)` 없음 → 3개월, 있음 → 그 값 − 2일)을 별도 순수
  함수로 분리해 날짜 계산만 테스트. `_run_sync` 통합은 기존 리뷰/매출
  스크래퍼 테스트와 같은 페이크 page/response 패턴으로, 이번 달 매출
  보완과 개별 주문 저장이 서로 독립적으로 실패해도 격리되는지 회귀
  테스트. `fetch_orders`(Playwright 화면 조작, 기존 `fetch_current_
  month_orders`의 일반화일 뿐 로직 변경 없음)는 이 저장소 컨벤션대로
  자동화된 pytest로 덮지 않는다 — 시그니처만 바뀌므로 기존 함수가 이미
  안정적으로 동작한다는 사실은 그대로 유효하고, 날짜 범위 인자를 다르게
  넘겨도 동작이 같은지만 실 계정 재확인으로 검증한다.
- **frontend**: `tsc --noEmit`. 로컬에서 (1) 배포 시 1회 실행하는 Mock
  정리 SQL을 로컬 검증 DB에도 실행 → (2) "데이터 동기화" 실행 → (3)
  주문내역 화면에 배민 실제 주문만(요기요/쿠팡이츠 Mock 없이) 뜨는지,
  메뉴명·주문유형·금액이 배민 사이트에서 직접 확인한 값과 맞는지 확인.
  (4) 이어서 "데이터 동기화"를 한 번 더 실행해 두 번째 호출이 눈에 띄게
  빨리 끝나는지(전체 3개월이 아니라 최근 며칠만 다시 긁으므로) 체감
  확인.

"배민 정산 상세(수수료/배달비/고객할인/우가클비용) 연동 (예외 허용)" 절
바로 아래에 "배민 주문내역(개별 주문) 연동 (예외 허용)" 절을 추가한다.

## 범위 밖

- 요기요/쿠팡이츠 실데이터 연동.
- 진행 중(미완료) 주문 — 이 화면 자체가 `CLOSED` 상태만 보여주는 것으로
  보임(실측 확인, 위 "조사 과정에서 확인된 사실" 참고). 진행 중 주문을
  보여주는 기능이 필요해지면 별도 조사·설계.
- 주문 취소/환불 반영 — 배민이 취소된 주문을 이 화면에서 어떻게
  표시하는지(상태값이 따로 있는지, 아예 안 보이는지)는 이번 조사에서
  확인하지 않았다. 필요해지면 별도 조사.
- `menu_summary` 200자 초과 시 손실 없는 전체 메뉴 목록 저장(현재
  `items[]` 배열에 옵션까지 다 있지만, `orders` 테이블은 요약 문자열
  하나만 저장하는 기존 스키마를 그대로 따른다).
