# 배민 데이터 동기화 증분 조회 설계

## 배경 / 목적

"데이터 동기화" 버튼을 실제 배포 환경(Railway + 크롤 워커)에서 처음
끝까지 돌려보니 최초 동기화가 22분 걸렸다(2026-08-19 실측, 데모 계정
`demo@dris.kr` / 치킨대장 당고점). 원인을 뜯어보니 6개 데이터 소스 중
`orders`(개별 주문내역)만 `compute_order_sync_range`로 진짜 증분
동기화이고, 나머지는 매 동기화마다 이미 가진 데이터까지 전부 다시
긁고 있었다:

| 데이터 | 증분 여부 | 매번 조회 범위 |
|---|---|---|
| 개별 주문내역(`orders`) | 이미 증분 | 커서 없으면 3개월, 있으면 커서−2일~오늘 |
| 리뷰 | 전체 재조회 | 매 매장마다 전체 페이지네이션 |
| 월별 매출(가게통계) | 전체 재조회 | 매번 완료된 3개월 전부 |
| 재주문율(crmInfo) | 전체 재조회 | 위 가게통계 방문에 얹혀 옴(최근 7일 고정) |
| 입금(정산내역) | 전체 재조회 | 매번 최근 90일 전부 |
| 정산 상세(카드클릭) | 전체 재조회 | 매번 최근 30일 카드 전부 클릭 |
| 우가클(브랜드별 광고 성과) | 전체 재조회 | 매번 4개 브랜드 × 3개월 전부 |

이 문서는 `orders`를 뺀 나머지 5개(리뷰/월별매출/재주문율/입금/정산상세/
우가클)에 같은 "이미 가진 건 건너뛴다" 원칙을 확장 적용하는 설계다.
버튼을 누르면 동기화가 시작되는 흐름 자체는 바뀌지 않는다 — 이 작업은
속도만 개선한다. 버튼을 안 눌러도 자동으로 도는 백그라운드 스케줄러는
이 설계가 끝난 뒤 별도로 브레인스토밍한다(범위 밖 절 참고).

## 소스별 설계

### 1. 리뷰 — 연속 known-ID 조기종료

`_run_sync`(`backend/app/review_sync.py`)는 매장(`shop_no`)마다
`fetch_all_reviews(session.page, shop_no)`로 전체 리뷰를 페이지네이션
하며 가져온 뒤, `existing_ids`(이미 저장된 `external_review_id` 집합)에
있는 것만 insert를 건너뛴다 — DB 중복은 막지만 스크래핑 자체는 매번
전체를 훑는다.

목록이 최신순이므로, 페이지네이션 도중 **이미 저장된
`external_review_id`가 연속 5개 나오면 그 시점에서 그 매장의 리뷰
조회를 중단**한다. 한두 개가 우연히 이미 있는 ID여도(예: 사장님이
직접 배민 앱에서 답글만 나중에 단 경우 등 순서가 살짝 어긋나는 경우를
방어) 바로 멈추지 않고, 5개 연속으로 전부 이미 아는 ID일 때만 안전하게
멈춘다. 매장(브랜드)별로 독립 적용 — 브랜드 A는 신규 리뷰가 많고
브랜드 B는 없으면 각자 다른 시점에 멈춘다.

`fetch_all_reviews`는 이 조기종료 조건을 판단할 수 있도록 이미 아는
ID 집합(`existing_ids`)을 인자로 받아야 한다(현재는 안 받음) — 시그니처
변경이 필요하다.

### 2. 월별 매출(가게통계) — 이미 있는 달은 건너뛰기 + crmInfo 방문 보장

`fetch_shop_stats`는 `recent_months(3)`이 돌려주는 "완료된 3개월"을
매번 전부 방문해 매출(`/v3/statistics/orders/summary`)과 재주문율
원본(`/v3/dashboard/crmInfo`)을 같이 가로챈다.

- **매출**: `daily_settlements`에 이 store_id+platform_id 기준으로
  해당 월에 `sales_amount IS NOT NULL`인 날짜가 하루라도 있으면 그
  달은 매출 fetch 대상에서 제외한다. `daily_settlements`는 매출/입금/
  정산상세 4개 컬럼이 같은 행을 공유하는 테이블이라(nullable 컬럼
  설계) "행이 존재하는지"만 보면 다른 소스(예: 입금만 먼저 채워진 날)
  때문에 매출을 잘못 건너뛸 수 있다 — 그래서 반드시 `sales_amount`
  컬럼 자체의 NULL 여부로 판단한다(3번·4번의 `deposit_amount`/
  `commission_amount` 컬럼별 판단과 같은 원칙). "완료된 달"은 배민
  쪽에서도 더 이상 안 바뀌는 확정치라는 전제다(CLAUDE.md에 이미
  문서화된 가정).
- **재주문율(crmInfo)**: 이 API는 어느 월 페이지를 보든 상관없이 항상
  "최근 7일" 고정 스냅샷만 준다 — 날짜 소급이 안 된다. 그래서 매출을
  3개월 다 건너뛰더라도, crmInfo만은 낡아지지 않도록 **매 동기화마다
  가장 최근에 방문 가능한 월 화면은 반드시 한 번 방문**한다(매출 fetch
  스킵 여부와 무관하게 crmInfo 캡처는 항상 시도). 이 방문 하나가
  `fetch_shop_stats`의 최소 호출 단위가 된다 — 3개월이 전부 이미
  동기화된 매장이라도 Playwright 작업이 완전히 0이 되지는 않고, 월
  하나만큼의 페이지 이동/대기로 줄어든다.

`fetch_shop_stats(page, shop_no, months)`의 `months` 인자를 호출부에서
위 필터링을 거친 목록으로 좁혀서 넘기면 되므로, 이 함수 자체의
시그니처는 바뀌지 않는다 — `_run_sync`가 어떤 달을 넘길지 결정하는
로직만 새로 추가한다.

### 3. 입금(정산내역, 90일) — 커서−2일 방식

`fetch_account_settlement(page, start_date, end_date)`는 매번
`today − 90일`부터 오늘까지 고정 조회한다.

`orders`와 동일한 패턴으로 바꾼다: `daily_settlements`에서 이 store_id+
platform_id 기준 `deposit_amount IS NOT NULL`인 가장 최근
`settle_date`를 커서로 삼는다.
- **커서 없음**(최초 동기화): 기존처럼 90일 전체.
- **커서 있음**: `커서 − 2일` ~ 오늘만 조회. 2일 여유는 `orders`와 같은
  이유(배치 상태가 동기화 시점 이후 확정될 수 있음).

기존 "조회 범위 안의 기존 행을 0으로 리셋 후 실제 배치로 다시 채우는"
갭 처리 로직(정산 배치가 없는 날짜를 Mock 오염 없이 0으로 남기는 용도)은
그대로 유지하되, 리셋 대상 범위도 좁아진 조회 범위(`커서−2일`~오늘)로
자동으로 따라 좁아진다 — 이미 그 범위를 파라미터로 받는 구조라 별도
수정이 필요 없다.

### 4. 정산 상세(카드클릭, 30일) — 커서−2일 방식

`fetch_settlement_breakdown_details(page, start_date, end_date)`도
매번 `today − 30일` 고정이다. 3번과 동일한 패턴: `daily_settlements`에서
`commission_amount IS NOT NULL`인 가장 최근 `settle_date`를 커서로
삼아 커서 없으면 30일 전체, 있으면 `커서−2일`~오늘만 카드를 클릭한다.

이 소스가 원래 가장 비쌌다(카드 하나당 클릭+대기 ~1.5초, 실측 최대
30페이지) — 대부분의 동기화에서 실제로는 최근 며칠치 카드 몇 개만
클릭하면 되므로 체감 개선 폭이 가장 클 것으로 예상한다.

### 5. 우가클(브랜드별 광고 성과, 3개월) — 완료된 달만 건너뛰기

`fetch_brand_click_metrics(page, shop_no, months)`도 브랜드마다 3개월
(이번 달 포함) 전부를 매번 방문한다. 설계 문서(`2026-08-12-baemin-
brand-ad-click-performance-design.md`)에 이미 "이번 달 포함 최근
3개월"로 명시돼 있어 진행 중인 이번 달은 원래도 매번 최신 상태로
갱신돼야 하는 대상이다.

- `brand_ad_click_metrics`에서 이 `shop_no` 기준으로 해당 월의 날짜가
  하루라도 있으면 그 달은 건너뛴다(2번과 동일한 "행 존재로 판단"
  기준).
- 이번 달은 정의상 아직 데이터가 계속 쌓이는 중이므로 이미 행이 있어도
  **항상** 재조회 대상에 포함한다(단순히 "해당 월이 오늘이 속한 달이면
  무조건 포함"으로 처리 — 별도 완료 여부 판단 불필요, 가게통계와 달리
  배민이 진행 중 달을 아예 안 주는 화면이 아니기 때문).

CPC 입찰가 조회(`fetch_cpc_booking`)는 매번 한 번씩만 호출되는 가벼운
작업이라 이번 증분 대상에서 제외한다(그대로 매번 조회).

## 커서 계산 방식 — 새 상태 없음

5곳 모두 새 컬럼이나 새 테이블을 추가하지 않는다. 매 동기화 시작 시
해당 테이블에서 `SELECT MAX(...)`/`SELECT EXISTS(...)`로 커서를
그때그때 계산한다 — `orders`가 이미 쓰는 패턴과 동일하고, CLAUDE.md의
정규화 원칙("매출 요약은 별도 테이블로 저장하지 않는다")과 같은
정신이다.

이 방식은 부수적으로 실패에 안전하다: 특정 소스의 fetch가 이번 동기화에서
실패하면 그 구간의 행이 애초에 안 생기므로, 커서도 그만큼 전진하지
않는다 — 다음 동기화가 자동으로 같은(또는 더 넓은) 구간을 다시 시도한다.
별도의 "실패 시 커서 롤백" 로직이 필요 없다.

## 최초 동기화 동작은 바뀌지 않는다

연결 직후 첫 동기화(위 5곳 모두 커서/기존 행 없음)는 지금과 완전히
동일하게 전체 백필한다(리뷰 전체 페이지네이션, 매출 3개월, 입금 90일,
정산상세 30일, 우가클 3개월). 이 설계는 **두 번째 이후 동기화만**
빨라진다.

## 순수 함수 추출

`compute_order_sync_range`와 같은 패턴으로, 각 소스의 "기존 데이터 →
이번에 조회할 범위/대상" 판단을 순수 함수로 뽑아 `backend/scrapers/
baemin_stats.py`에 둔다(리뷰의 조기종료 판단은 `backend/scrapers/
baemin_reviews.py`에 둔다 — 그 모듈이 리뷰 페이지네이션을 담당하므로).
Playwright를 직접 다루는 부분은 계속 pytest로 커버하지 않는다(기존
관례 그대로).

새로 추출할 함수(가칭, 실제 이름/시그니처는 구현 단계에서 확정):
- `should_stop_review_pagination(recent_ids, existing_ids, threshold=5) -> bool`
  (또는 페이지네이션 루프 안에 인라인 — 구현 단계에서 판단)
- `filter_months_needing_sync(months, synced_months) -> list[str]` — 2번(매출)과
  5번(우가클)이 공유 가능한 "이미 그 달 행이 있는지" 필터. 다만 5번은
  "이번 달은 항상 포함" 규칙이 추가로 붙으므로 호출부에서 그 예외를
  얹거나 별도 파라미터로 받는다.
- `compute_settlement_sync_range(latest_settled_date, today) -> tuple[date, date]` —
  `compute_order_sync_range`와 동일한 시그니처/동작(3번·4번 공용 —
  둘 다 "커서 있으면 −2일~오늘, 없으면 전체 기본폭" 패턴이지만 기본폭이
  90일/30일로 다르므로 기본폭을 인자로 받는다).

## 테스트 계획

- `filter_months_needing_sync`류: 빈 목록(전부 미동기화) → 입력 그대로
  반환, 일부 이미 동기화 → 나머지만 반환, 전부 이미 동기화 → 빈 목록.
- `compute_settlement_sync_range`류: 커서 없음 → 기본폭 전체, 커서
  있음 → 커서−2일~오늘, 커서가 오늘이면 → 오늘−2일~오늘(퇴화 케이스도
  에러 없이 동작 확인).
- 리뷰 조기종료: fake page/응답으로 "연속 5개 이미 아는 ID" 시나리오와
  "중간에 신규 하나 섞여 연속이 끊기는" 시나리오를 구분해서 검증.
- `review_sync.py` 통합 테스트(기존 fake-page 패턴 확장): 두 번째
  동기화 시뮬레이션에서 이미 있는 달/이미 있는 정산 구간을 실제로
  건너뛰는지, crmInfo 방문은 매출을 다 건너뛴 경우에도 여전히 일어나는지
  확인.
- 회귀 확인: 최초 동기화(모든 커서 없음) 경로가 기존 테스트대로 여전히
  전체 백필하는지 그대로 유지되는지 확인.

## 범위 밖

- **자동 백그라운드 스케줄러**: 버튼을 안 눌러도 주기적으로 동기화가
  도는 기능은 이 설계에 포함하지 않는다 — 이 설계가 구현된 뒤 별도로
  브레인스토밍한다.
- **오래 묵은 커서에 대한 특수 처리**: 수십~수백 일 동안 동기화를 안
  한 경우를 위한 별도 캡/경고는 두지 않는다. 커서가 오래됐으면 그만큼
  넓은 범위를 자연스럽게 다시 조회할 뿐이고, 기존 부분수집 하드 에러
  (`BaeminStatsScrapeError`)가 여전히 안전망 역할을 한다.
- **리뷰 답글이 배민 앱에서 직접 달린 경우의 재동기화**: 이미 저장된
  리뷰에 나중에(우리 앱이 아니라 배민 사장님광장에서 직접) 답글이 달려도
  이 설계는 그 리뷰를 다시 안 본다 — 이건 증분 여부와 무관하게 기존
  설계부터 있던 제약이라 이번 범위에서 다루지 않는다.
