# 광고 순위 모니터링 재설계 — 실데이터 CPC + 4브랜드 + 입찰 조정 설계

## 배경

기존 "광고 순위 모니터링"(2026-08-15 계획)은 치밥대장 브랜드 하나만 실데이터로 연동했고,
"현재 CPC"는 처음부터 한 번도 실제로 갱신된 적 없는 seed 값(400원)을 그대로 보여주고
있었다. 실사용자 테스트로 다음 문제가 드러났다:

1. "현재 CPC"가 실측이 아니라 2026-08-11 seed 값(400원/300원)이 고정으로 남아있다
   (`ad_campaigns.current_cpc`를 갱신하는 코드가 어디에도 없음을 확인).
2. "경쟁 예상 CPC"는 배민이 구조적으로 노출하지 않는 값이라 지금까지 파생 추정치
   (`current_cpc * 1.15`)로만 표시해왔는데, 이마저 갱신 안 되는 `current_cpc`에
   기반해 사실상 의미 없는 고정값이었다.
3. 화면에 "Mock 스냅샷"이라는 문구가 남아있어 사용자가 데이터 신뢰도를 오해할 수 있다.
4. 한 사업자가 배민 계정 하나로 최대 4개 브랜드(치밥대장/곱도리탕/블랙닭갈비/
   행복가성비)를 운영하는데, 지금은 치밥대장 하나만 다룬다.
5. 사용자가 원하는 순위까지 CPC를 직접 얼마씩 올려가며 배민 앱에서 순위를 확인하는
   작업을 수동으로 반복하고 있다 — 이 반복 확인을 자동화하고 싶어 한다.

### 실측 조사 결과 (2026-08-18, 실 계정 라이브 검증)

- **"클릭당 희망 광고금액"(현재 CPC) 데이터 출처**: 사장님광장 "광고·서비스관리"
  화면(`/shops/{shopNo}/ad/campaign`)이 로드될 때 호출하는
  `GET https://self-api.baemin.com/v4/cpc/bookings/by-shop-number?shopNumber={shopNo}`
  응답의 `bid` 필드. 실측(치밥대장, shop_no=14804318): `bid: 95`(원),
  `maxBid: 860`(원), `monthlyBudget: 1000000`, `spentBudget: 150065`,
  `isAutoBidding: false`. 화면의 "우리가게클릭 → 화살표 펼치기 → 광고·서비스 →
  클릭당 희망 광고금액: 95원" 표시와 정확히 일치함을 직접 확인했다.
- **입찰가 수정 화면**: 같은 화면에서 "광고·서비스" 섹션의 "수정" 링크를 누르면
  "광고 금액 수정" 모달이 뜬다. "희망가 조정 방식"으로 "스마트 모드"(배민이
  30원~설정한 최대 희망가 사이에서 자동 최적화)와 "수동 설정 모드"(직접 설정한
  희망가로 고정) 중 선택할 수 있고, 지금은 "수동 설정 모드"가 기본 선택돼 있다.
  "월 예산"/"클릭당 희망 광고금액" 입력 필드와 "적용" 버튼이 있다. **이번
  기능은 항상 "수동 설정 모드"를 전제로 한다** — 배민의 "스마트 모드"는 우리가
  관여할 수 없는 자체 최적화라 이번 스코프 밖.
- **실제 제출(쓰기) API는 아직 캡처하지 못했다** — "적용" 버튼을 실제로 눌러서
  요청을 관찰하는 건 사용자 계정에 진짜 쓰기 작업이라, 조사 단계에서 멈추고
  사용자 승인 하에 구현 단계에서 확인하기로 했다(아래 "구현 시 라이브 검증
  필요" 참고).
- **4개 브랜드의 shop_no/카테고리는 이미 로컬 DB에 있다**(`baemin_shop_brands`
  테이블, 이전 실동기화로 이미 upsert됨 — 재조사 불필요):

  | 브랜드 | shop_no | 카테고리 |
  |---|---|---|
  | 치밥대장 숯불양념92치킨 노원당고개점 | 14804318 | 치킨 |
  | 곱도리탕 진짜 잘하는집 노원당고개점 | 14804912 | 찜·탕·찌개 |
  | 블랙닭갈비 노원당고개점 | 14804914 | 고기·구이 |
  | 행복가성비 컵밥&우동 노원당고개점 | 14805005 | 백반·죽·국수 |

  (카테고리는 `baemin_shop_brands.shop_name` 문자열의 " / " 구분자 뒤,
  shop_no 앞 부분을 그대로 쓴다 — 예: `"... / 찜·탕·찌개 14804912"` →
  `"찜·탕·찌개"`. 새 파싱 로직이 필요 없다 — `fetch_shop_info(shop_no)`가 이미
  `categories[0].name`을 정확히 파싱해서 반환하므로, 카테고리는 이 기존
  함수를 4개 shop_no 각각에 호출해서 얻는다.)

### 입찰 자동화 범위에 대한 논의 (중요한 결정)

원래 사용자는 "목표 순위를 입력하면 시스템이 알아서 CPC를 계속 올리면서 순위를
확인하는" 완전 자동화를 원했다. 이건 진행하지 않기로 했다 — 이유:

1. `CLAUDE.md`의 "절대 금지" 목록에 "실제 CPC 자동 입찰 금지"가 명시돼 있고,
   지금까지 예외를 준 항목은 전부 **읽기 전용**(로그인, 리뷰, 매출, 순위 크롤링)
   이었다. CPC를 실제로 바꾸는 건 이 프로젝트에서 처음 시도하는 **쓰기** 액션이라
   위험 등급이 다르다.
2. 이 세션에서 실측으로 CPC 변경 없이도 순위가 25위→7위로 크게 바뀌는 걸 직접
   목격했다 — 순위는 CPC 말고도 여러 변수(시간대, 경쟁사 입찰, 배달권역 등)의
   영향을 받아서, "목표 미달성 = CPC를 더 올려야 함"이라는 단순 추론이 항상
   맞지 않는다. 완전 자동화하면 실제로는 CPC와 무관한 노이즈를 좇아 예산을
   낭비할 위험이 있다.
3. 배민은 경매형 구조라 경쟁사도 실시간으로 입찰을 올릴 수 있어, 완전 자동화된
   추격 로직은 밑도 끝도 없는 입찰 전쟁으로 이어질 수 있다.

**합의된 대안**: 순위 재측정(크롤)은 자동화하되, **실제 금액이 배민에 반영되는
"적용" 버튼은 항상 사용자가 직접 클릭**한다. 사용자가 목표 순위와 시도할 금액을
직접 입력 → "적용하기" 클릭(배민에 실제 반영됨을 명시한 확인 문구 포함) →
자동으로 순위 재측정 실행 → 결과를 보고 다음 시도 금액을 **추천**만 한다(자동
적용 안 함). 추천 단계 폭은 사용자가 먼저 제안한 10~50원 범위 중 기본값
30원을 쓴다.

## 1. 데이터 모델

```sql
-- ad_rank_snapshots에 컬럼 추가: 그 순간의 CPC를 같이 기록해야 나중에
-- "이 CPC일 때 이 순위였다"는 이력을 추천 근거로 쓸 수 있다.
bid_at_snapshot INT  -- nullable, 실측 당시 ad_campaigns.current_cpc 스냅샷
```

`ad_campaigns`에 3개 브랜드 캠페인을 추가한다(스키마 변경 없음, INSERT만):
곱도리탕(shop_no=14804912, category=찜·탕·찌개), 블랙닭갈비(shop_no=14804914,
category=고기·구이), 행복가성비(shop_no=14805005, category=백반·죽·국수).
`current_cpc`/`target_rank` 초기값은 데이터 동기화 첫 실행 시 실측으로 채워지기
전까지는 임시값(추후 동기화로 즉시 갱신됨)으로 둔다.

## 2. 백엔드

**읽기 스크래퍼** — `backend/scrapers/baemin_ads.py`에 추가:
```python
def fetch_cpc_booking(page, shop_no: str) -> dict:
    """GET /v4/cpc/bookings/by-shop-number?shopNumber={shop_no}를 가로채
    {bid, max_bid, monthly_budget, spent_budget, is_auto_bidding}을 반환한다."""
```
"데이터 동기화" 버튼을 누를 때(`review_sync.py`) 배민 연결의 4개 브랜드 각각에
대해 이 함수를 호출해 `ad_campaigns.current_cpc`를 실측으로 갱신한다.

**쓰기 스크래퍼(신규, 이 프로젝트 첫 쓰기 액션)** — 정확한 제출 API는 구현
태스크에서 실 계정으로 "적용" 버튼을 한 번 직접 눌러보며 확인한다(사용자와
함께, 실제로 반영될 금액임을 사전에 확인받고 진행). "수동 설정 모드"가 선택된
상태를 유지하고 "클릭당 희망 광고금액" 필드만 사용자가 지정한 값으로 바꿔
제출한다.

**API 엔드포인트** (`backend/app/routers/ads.py`에 추가):
- `POST /ads/rank-by-distance/apply-bid` — `{campaign_id, amount}`. 서버가
  스크래퍼로 배민에 실제 금액 반영 → 성공하면 `ad_campaigns.current_cpc` 갱신
  → 곧바로 기존 순위 재측정 크롤(`_start_crawl_job`)을 이어서 트리거.
- 기존 `GET /ads/rank-monitoring`, `GET /ads/rank-by-distance`가
  `campaign_id` 쿼리 파라미터를 받아 4개 브랜드 중 하나를 선택할 수 있게 한다
  (지금은 사실상 첫 캠페인 하나만 가정하는 구조).
- 추천 로직(간단한 함수, 새 모듈 불필요 — `ads.py` 안에 헬퍼 함수로): 최근
  실측 순위가 `target_rank`보다 나쁘면 `current_cpc + 30`을 추천값으로,
  달성했으면 "유지" 상태를 반환.

## 3. 프론트엔드

- `frontend/src/app/(app)/ads/page.tsx`: "Mock 스냅샷" 문구 제거(4개 브랜드
  전부 실데이터이므로 안내 문구 전체 갱신), "경쟁 예상 CPC" 컬럼 제거.
- 브랜드 4개를 탭 또는 드롭다운으로 선택하는 UI 추가, 선택된 `campaign_id`로
  나머지 카드들을 갱신.
- "목표 순위"(숫자 입력, 기존 `target_rank`와 별개로 즉시 편집 가능하게) +
  "시도할 CPC 금액"(숫자 입력, 현재 CPC로 기본값 채움) + "적용하기" 버튼.
  버튼 클릭 시 "OO원으로 배민에 실제 반영됩니다. 계속할까요?" 확인 다이얼로그
  → 확인하면 `POST /ads/rank-by-distance/apply-bid` 호출 → 성공 시 기존
  크롤 진행 상태 UI(이미 있음, "순위 확인 중...")로 자동 전환 → 완료되면 결과
  + 추천 문구("아직 목표(3위)보다 낮아요(7위). 30원 더 올려서 125원으로
  시도해보는 걸 추천해요." 또는 "목표를 달성했어요!") 표시.

## 4. 구현 시 라이브 검증 필요 (알려진 리스크)

- CPC 제출(쓰기) API의 정확한 엔드포인트/페이로드 — 위에서 설명한 대로 조사
  단계에서 의도적으로 멈췄다. 구현 태스크에서 사용자에게 실제로 반영될 금액을
  미리 알리고, 동의 하에 실 계정으로 한 번 제출해 요청 형식을 확인한다.
- "적용" 성공 후 배민 쪽 반영에 시차가 있을 수 있다(화면 안내문구 "우리가게클릭
  설정 변경 시 서비스에 반영되기까지 일정 시간이 소요될 수 있습니다" 확인함) —
  적용 직후 바로 순위를 재측정하면 아직 반영 전일 수 있으므로, 크롤 시작 전에
  짧은 대기(구현 시 적정 시간 결정, 우선 30초 제안)를 둔다.

## 스코프 밖 (YAGNI)

- 배민의 "스마트 모드"(자동 최적화) 연동 — 항상 "수동 설정 모드"만 다룬다.
- 완전 자동 반복 입찰(목표 도달까지 무인 루프) — 위 논의대로 각 단계마다 사용자
  승인 필요.
- 4개 브랜드를 동시에 순위 재측정 — 크롤은 에뮬레이터 하나로 순차 실행만
  가능(기존 `_crawl_lock` 제약 그대로).
- CPC 인하(다운) 추천 — 이번엔 목표 미달 시 증액 추천만 다룬다.
