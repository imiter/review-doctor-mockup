# 리뷰 답글 AI 에이전트 + LLMOps 재설계

> **설계 완료, 사용자 리뷰 대기 중** (2026-10-06) — 1~4절 전체 설계가
> 끝났다. 자체검토 완료, git 커밋은 사용자가 이 문서를 확인한 뒤 한다.

## 배경

실 SaaS로 광고를 집행하기 전에, 지금 RAG 방식으로만 돌아가는 리뷰 답글
파이프라인(`backend/app/llm/`)을 제대로 된 "AI 에이전트" + LLMOps 설계로
다시 짠다. 최종 목표는 이 사장님 한 명의 가게에만 쓰는 게 아니라, **여러
매장이 구독료를 내고 쓰는 범용 AI SaaS**로 운영하는 것이다 — 이 목표가
아래 메모리 구조 설계(특히 절차 기억을 전역으로 둔 결정)의 전제가 됐다.

사용자가 하나부터 열까지 직접 설계·구축하고 싶어해서, 완성된 설계를
한 번에 제시하지 않고 한 단계씩 같이 결정하며 진행한다.

## 처음부터 지켜야 할 제약 (이미 구현되어 있음 — 재구현 아님)

- **"훈련카드" 콜드스타트**: 이미 `OnboardingScenario`/
  `backend/app/routers/reply_onboarding.py`로 구현돼 있음(하루 3개 트리클,
  `find_uncovered_categories`/`get_or_create_scenario`). 사장님이 답변하면
  `GoldenExample(is_manual=True, source="onboarding")`로 바로 승격.
- **부정 리뷰 이모지 금지**: 이미 `_COMPLAINT_TONE_OVERRIDE`
  (`backend/app/llm/generate.py`)로 구현돼 있음, `category != "no_issue"`
  전체에 적용(CLAUDE.md "no_issue 리뷰도 RAG로 통합" 절 참고).

## 설계 방법론

CoALA(절차/의미/일화 기억) 프레임워크로 구조화해서 진행. 순서: 메모리
구조 → 에이전트 추론 루프 → LLMOps 관측성 → (선택) DeepTwin 원칙 증류.
첫 단계로 메모리 구조부터 시작하기로 사용자가 선택.

## 1. 메모리 구조 (완료)

### 1.1 절차 기억 (Procedural)

지금 `backend/app/llm/generate.py`에 하드코딩된 지시문들을 DB 테이블로
분리한다. 현재 하드코딩돼 있는 것들(CLAUDE.md에 이미 문서화됨):

- `_COMPLAINT_TONE_OVERRIDE`: "이모지 없이 차분하고 진중하게"
  (`category != "no_issue"`일 때)
- few-shot 프롬프트의 "스타일만 참고, 사건 내용 복사 금지" (항상 적용,
  과적합 방지)
- 메뉴 그라운딩 지시: "리뷰가 특정 메뉴/재료를 언급하면 이 정보를 근거로
  삼고, 실제 구성과 다른 원인은 추측해서 쓰지 마라"
- "찐사장님 말투" 톤 지시: "페르소나에 맞춰 임의로 바꾸지 말고 사장님의
  실제 말투를 그대로 따르라"
- no_issue 프레이밍: "특이 불만 없음(칭찬 또는 중립적인 리뷰), 구체적
  취향/요청이 있으면 반영"
- **(신규 제안) `delivery` 카테고리 책임 경계 규칙**: "배달 지연·파손·
  라이더 응대 등 가게가 직접 통제할 수 없는 배달 과정 불만에는 공감과
  유감을 표현하되, 가게가 전적으로 책임지거나 무조건 '수정하겠습니다'라고
  약속하지 않는다. 가게 책임이 아님을 부드럽게 알리면서도 고객 불편엔
  공감하는 균형을 유지한다." — 2026-10-06 확정. 이모지 금지 규칙과 같은
  성격(매장별 취향이 아니라 모든 구독 매장에 적용되는 상식적 원칙)이라
  처음부터 procedural_rules에 포함한다.

**관련 수정 (신규 제안)**: 위 규칙이 제대로 걸리려면 `classify.py`의
`delivery` 카테고리 설명도 "배달 지연, 파손에 대한 불만"에서 **"배달
지연·파손·라이더(배달원) 응대 등 배달 과정에서 발생한 불만"**으로
넓혀야 한다 — 지금 설명으로는 "라이더가 불친절했다"가 `service`(가게
직원 응대, 가게가 통제 가능한 영역)로 잘못 분류될 수 있다. `service`는
가게가 통제 가능한 것, `delivery`는 배달 과정에서 생기는 가게 통제
밖의 것으로 경계를 명확히 한다(2026-10-06, 실제 카테고리 커버리지를
점검하다 발견한 구멍).

**조건 판단은 Python 코드에 그대로 둔다** — 언제 어떤 규칙을 적용할지
판단하는 if/elif 로직은 손대지 않고, **지시문 텍스트만** DB에서 조회해
꽂아 넣는다. 조건 자체를 데이터로 표현하는 규칙 엔진은 만들지 않는다
(지금 규칙 5개 규모에 과한 설계).

**전역 테이블, `store_id` 없음** — 이 규칙들은 "이 AI 제품이 어떻게
답글을 쓰는가"에 대한 제품 차원의 품질/안전 기준이지, 매장별 취향이
아니다(매장별로 다르게 하고 싶은 건 이미 `reply_settings`가 맡고 있음).
여러 매장이 구독하는 SaaS로 갈수록 오히려 이 규칙은 모든 구독자에게
동일하게 적용돼야 하는 전역 기준이라는 게 더 분명해진다. 나중에 "매장별
톤 규칙 커스터마이징" 같은 게 실제 제품 기능으로 요청되면 `reply_settings`
확장으로 별도 다룬다.

```sql
procedural_rules
- id (PK)
- rule_key (UNIQUE, 예: complaint_tone_override, few_shot_anti_overfit,
  menu_grounding, no_issue_framing)
- instruction_text (실제 프롬프트에 꽂히는 지시문)
- active (bool, 코드 배포 없이 끄고 켤 수 있게)
- description (나중에 관리 화면을 위한 사람이 읽을 설명)
```

### 1.2 의미 기억 (Semantic)

기존 `store_style_profile`(매장별 답글 스타일 규칙 캐싱) +
`brand_menu_info`(가게소개/원산지/메뉴소개)는 그대로 유지.

**신규 소스: 사장님공지**. "주문안내"는 사용자가 함께 제안했으나 실측
결과 신규 데이터가 아니라 이미 `brand_menu_info.menu_intro`로 수집되고
있던 필드임이 확인됐다(API 필드명은 `menuIntro`지만 실제 사장님광장 UI
탭 이름이 "주문안내").

- 엔드포인트: `GET https://self-api.baemin.com/v1/review/shops/{shopNo}/ceo/notices?offset=0&limit=10`
  — 기존 리뷰 스크래핑과 같은 API 네임스페이스(`/v1/review/shops/...`)지만,
  사장님광장 좌측 메뉴의 "리뷰관리"와는 별도인 "사장님공지" 메뉴를
  클릭해야 발생한다.
- 응답 구조: `{"next": bool, "notices": [{"id", "shopNumber", "contents"
  (자유 텍스트), "images": [...], "createdAt", "displayStatus",
  "blockType", "blockMessage"}]}`.

**저장**: 새 테이블 `brand_ceo_notices`(공지 1건 = 1행, 기존
`baemin_shop_brands`/`brand_ad_click_metrics`와 같은 "항목당 한 행"
패턴). 이미지는 저장하지 않는다 — 지금 파이프라인에 vision 호출이 전혀
없어서 당장 쓸 데가 없음(YAGNI).

```sql
brand_ceo_notices
- id (PK)
- store_id (FK → stores)
- platform_id (FK → platforms)
- shop_no (값만 저장, FK 아님 — brand_ad_click_metrics와 동일 관례)
- external_notice_id (API의 id)
- contents (TEXT, 공지 본문)
- display_status (API의 displayStatus)
- block_type (API의 blockType)
- notice_created_at (API의 createdAt)
- synced_at (우리가 긁어온 시각 — 30일 스킵 판단용)
```

**동기화 방식**: `brand_menu_info`의 `menu_info_needs_refresh`(30일 스킵)
패턴을 그대로 재사용 — 별도 "마지막 동기화" 추적 테이블을 만들지 않고,
이 테이블의 `synced_at` 컬럼의 `MAX()`를 그때그때 계산해 30일 이내면
사장님공지 수집 단계(사이드바 이동 포함) 자체를 건너뛴다. 동기화할 때는
**전체 교체(snapshot replace)** — 기존 행을 지우고 API가 지금 주는
목록으로 새로 채운다. 히스토리를 남기지 않는다 — 이 테이블의 유일한
용도가 "RAG에 넣을 현재 활성 공지"라서 과거 이력을 추적할 이유가 없다.

**RAG 주입**: `display_status=="DISPLAY"` AND `block_type=="NONE"`인
공지만 골라, 여러 개면 전부 이어붙여서 가게소개/원산지/메뉴소개와 같은
자리에 "사실 근거용" 텍스트로 주입한다.

### 1.3 일화 기억 (Episodic — `golden_examples`)

organic(`is_manual=true`, 사장님이 실제로 쓴 것)을 우선, onboarding은
부족분을 채우는 보충용. 블렌드/가중 랭킹이 아니라 `fetch_golden_examples`의
검색 단계 안에서 필터/폴백으로 동작: category 필터 → organic만 유사도
랭킹(pgvector) → organic 개수가 few-shot 슬롯을 못 채우면 그때만
onboarding으로 보충. 기존 `app/llm/rag.py`의 `fetch_golden_examples` 로직
위에 이 우선순위 규칙만 얹는다.

**golden_examples로 들어오는 3개 경로**(2026-10-06 정리):

- **경로 A (기존)**: 리뷰-답글 루프에서 보류된 리뷰를 사장님이 고쳐 써서
  `save_final_reply`로 저장 — `draft is None OR draft.content !=
  reply.content`일 때만 승격, `source="organic"`.
- **경로 B (기존)**: 훈련카드(`OnboardingScenario`)에 사장님이 답변 →
  `answer_scenario`가 diff 비교 없이 항상 승격, `source="onboarding"`.
- **경로 C (신규 제안, 미구현)**: 사장님이 배민에 **직접** 단 답글 —
  `review_sync.py`가 동기화 시점에 `extract_owner_reply`로 감지해
  `ReviewReply(reply_type="final")`로는 저장하지만(이중 답글 방지 목적),
  지금은 golden_examples 승격을 전혀 안 한다. 아래 1.4절에서 이 경로를
  신뢰도 있게 추가하는 방법을 설계한다.

### 1.4 일화기억 품질 필터링 (완료)

**문제**: `is_manual=true`(organic)로 표시된 기존 답글 중 일부가 사실
사장님이 다른 AI 도구로 생성해서 복붙한 것일 수 있다(CLAUDE.md에 이미
기록된 기존 700여 건 혼합 사례와 연결됨). "organic 우선"이라는 1.3절
설계 전체가 "organic=진짜 사장님 말투"라는 전제 위에 서 있는데, 이 전제가
깨지면 궁극 목표(진짜 사장님 말투 재현)를 훼손하는 설계가 된다.

**기각한 접근**: 텍스트 자체의 문체 분석이나 LLM에게 "이거 AI가 쓴
것 같아?"라고 묻는 방식은 AI가 AI를 탐지하는 셈이라 신뢰도가 낮아 기각.
사장님에게 기존 답글을 일일이 "직접 쓰신 거 맞아요?"라고 확인받는 방식도
기각 — 리뷰가 수천 건일 수 있는 매장은 현실적으로 하나하나 기억 못 하고,
"AI 추천 답글 + 직접 수정" 같은 중간 케이스도 많아 이분법 질문 자체가
안 맞음.

**채택한 접근 — 상황적 신호 기반 confidence scoring**: 텍스트 내용이
아니라 "이 상황이면 사장님이 직접 쓸 수밖에 없었다"는 맥락적 정황
신호 3개를 OR로 조합한다:

1. 그 가게의 리뷰 수가 ≤3일 때 쓴 답글(가게 초기, AI 도구를 쓸 상황
   자체가 아니었을 가능성이 높음)
2. 불만 카테고리(`category != "no_issue"`)
3. 별점-내용 불일치(`sentiment_conflict = true`)

**기각한 4번째 신호**: "파트너님에게만 보이는 리뷰"(배민 리뷰 API의
`displayType == "CEO_ONLY"`, 실측 확인됨)도 처음엔 후보였으나, 실제
캡처한 샘플(별 5점·CEO_ONLY·불만 없음 리뷰)에 달린 답글이 "변함없이
맛과 품질에 힘쓰겠습니다" 식의 정형화된 감사 인사였다 — 비공개라고
무조건 공들여 쓴 진짜 말투라는 보장이 없다는 게 실측으로 확인됨. 게다가
CEO_ONLY가 정말 의미 있어지는 경우(불만이 있어 공들여 답한 경우)는 이미
2·3번 신호가 잡아내므로 독립 신호로서 중복/무가치 — 채택하지 않는다.
`reviews`에 `display_type` 컬럼을 새로 저장할 필요도 없다(YAGNI).

**리트리벌 반영**: 완전히 버리는 대신(신호 없는 organic도 진짜 사장님이
쓴 짧은 답글일 수 있어 과한 추측), **3단계 우선순위**로 둔다:

1순위: organic(`is_manual=true`) + 위 3개 신호 중 하나 이상 보유
2순위: organic이지만 신호 없음
3순위: onboarding

category 필터 → 1순위 안에서 유사도 랭킹 → 모자라면 2순위로 보충 →
그래도 모자라면 3순위(onboarding)로 보충, 기존 1.3절 로직의 자연스러운
확장이다. 신호 계산은 컬럼으로 저장하지 않고 조회 시점에
`golden_examples.source_review_id`로 연결된 `reviews`를 JOIN해서 그때
계산한다(정규화 원칙 — 저장된 파생값 대신 조회 시 계산). `source_review_id`가
없는 golden_example(연결 안 된 경우)은 신호 없음으로 간주해 2순위로
취급한다.

### 1.4.1 경로 C(배민 직접 답글) 신뢰도 검증 (신규 제안, 2026-10-06)

**정정**: 경로 C를 처음 제안했을 때 "우리 AI 초안을 한 번도 안 봤으니
100% 직접 쓴 것"이라고 판단했는데, 이건 틀린 추론이었다 — 사장님이
우리 시스템이 아닌 **다른 AI 도구**(CLAUDE.md에 이미 기록된, 기존
700여 건이 "별도 AI 도구 + 직접 작성" 혼합이었던 것과 동일한 위험)로
답글을 만들어 배민에 그대로 붙여넣었을 수도 있다. 경로 C는 경로 A/B보다
**더 신뢰할 수 있는 게 아니라 오히려 구조적 보증이 가장 약한 경로**다
— 1.4절을 만든 이유(organic 전부를 무조건 신뢰할 수 없다)가 그대로
적용된다.

**2단계로 검증한다**:

1. **1단계 — 기존 1.4절 신호를 그대로 재사용**: 경로 C로 들어오는
   golden_example도 `source_review_id`를 정확히 연결해, 리뷰수≤3/불만
   카테고리/sentiment_conflict 신호를 동일하게 적용한다. 경로라고
   특별 취급하지 않는다.
2. **2단계(신규) — 임베딩 기반 말투 일관성 체크**: "AI가 썼는지"를
   직접 판별하는 대신(신뢰도 낮음, 이미 기각), **"이 가게의 이미
   구조적으로 신뢰할 수 있는 예시들(경로 A/B)과 임베딩이 일관되는가"**를
   본다 — 질문을 "진짜 사람이 썼나"에서 "이 가게 말투에 맞나"로 바꾸는
   것(어차피 궁극 목표가 후자다). 기존 Voyage/pgvector 인프라를 그대로
   재사용해 새 인프라가 거의 필요 없다. 경로 C 후보의 임베딩이 그 매장의
   경로 A/B 예시 클러스터와 충분히 가까우면 통과, 동떨어진 이상치면
   의심 표시. **전제조건**: 비교할 경로 A/B 예시가 그 매장에 충분히
   쌓여있어야 계산 가능 — 신생 매장은 기준점이 없어 이 체크를 건너뛴다.

**이상치로 걸린 경우의 처리**: 데이터를 버리지 않는다(1.4절과 같은
원칙) — golden_example로는 저장하되, 4.1절의 "원칙 확인" 화면과 같은
패턴으로 **의심되는 소수 건만** 사장님께 "이거 직접 쓰신 거 맞아요?"
확인받는다. 모든 리뷰를 확인받는 방식은 이미 기각했지만(위 1.4절,
"리뷰가 수천 건"), 이건 진짜 의심스러운 소수 건으로 범위가 좁혀져
있어 그 반대 논리가 적용되지 않는다.

## 2. 에이전트 루프/추론 설계

### 2.0 프레임워크 채택: LangChain + LangGraph + LangSmith

**이 AI 파트는 기존 코드/의존성을 기준으로 삼지 않고 처음부터 재설계하는
작업이다** — "지금 코드베이스에 LangChain이 없다"는 건 리팩토링 전
상태일 뿐, 새 설계의 제약이 아니다(2026-10-05, 사용자가 명시적으로
바로잡음). 사용자가 LLMOps를 공부하며 LangChain/LangGraph가 실제
업계 표준 개념이라고 확인했고, "하나하나 직접 해봤다"는 학습 목표에도
부합하므로 **LangGraph를 에이전트 루프의 상태 그래프로, LangSmith를
관측성으로 정식 채택**한다. `backend/app/llm/generate.py`/`rag.py`/
`client.py`의 LLM 호출부를 `langchain-anthropic`(`ChatAnthropic`)로
교체하는 실질적 구조 변경이 따른다 — "처음부터 재구축" 전제 안에서
감수하기로 함. 이미 확정한 메모리 구조(procedural_rules 테이블,
golden_examples pgvector 검색, brand_menu_info/brand_ceo_notices 조회)는
스키마 변경 없이 그대로 유지하고, LangGraph 노드 안에서 도구처럼
호출하는 방식으로 연결한다.

### 2.1 그래프 구조

**State**: 리뷰 원문/별점/category/sentiment_conflict(이미 분류됨),
store/브랜드 정보, 조회된 기억(절차/의미/일화), 초안, 검증 결과, 최종
답글.

**노드**:
1. `retrieve_memory` — 절차 기억(해당 규칙), 의미 기억
   (store_style_profile/brand_menu_info/brand_ceo_notices), 일화 기억
   (golden_examples 3단계 우선순위, 1.4절)을 조회해 state에 채움.
2. `generate_draft` — `ChatAnthropic` 호출, 조회된 컨텍스트로 초안 생성.
3. `verify_draft` — **결정론적 체크만**(LLM 자기비판 없음, 북극성 목표인
   "진짜 사장님 말투" 보존을 위해 — LLM 재판단을 거칠수록 말투가
   무난하게 수렴할 위험이 있다고 판단해 기각): (a) 이모지 규칙 위반,
   (b) few-shot 예시 문장 복붙 여부(문자열 유사도).
4. 조건부 분기: 위반 없음 → `finalize`. 위반 있음 → `fix_draft`.
5. `fix_draft` — 이모지 문제는 LLM 호출 없이 코드로 바로 제거(기존
   `_strip_emoji`와 동일). 복붙 유사도 문제는 "이 문장이 예시 X와 너무
   비슷하니 그 부분만 바꿔라"는 구체적이고 좁은 지시로 재생성(막연한
   "다시 평가해봐"가 아님) → `verify_draft`로 재검증.
6. `finalize` — 최종 답글 반환.

**재시도 한도**: `fix_draft`↔`verify_draft` 루프는 **최대 2회 재시도
(총 3번 생성 시도)**로 제한한다. 이모지 체크는 애초에 결정론적이라
재시도가 필요 없고, 실제로 재시도가 의미 있는 건 복붙 유사도 체크뿐이라
— 1~2번 안에 안 고쳐지면 더 반복해도 성공률이 크게 오르지 않는다고
판단.

**적용 범위 확대 (2026-10-05, 중요한 결정)**: 지금 자동답글은
`rating==5 AND category=="no_issue" AND not is_sensitive AND not
sentiment_conflict`로만 엄격히 제한돼 있다(CLAUDE.md "안전 게이트
강화" 절 — 실제 사고였던 리뷰 799건 이후 의도적으로 좁힌 안전장치).
이 루프의 검증+재시도+보류 메커니즘을 새 안전장치로 삼아 **불만
카테고리·저평점 리뷰도 자동답글 대상으로 확대**하기로 함 — 사용자가
명시적으로 "자동답글이 사장님 입장에서 제일 편한 기능"이라는 가치를
불만 리뷰까지 넓히고 싶다고 확인(기존의 블랭킷 카테고리 제외 대신, 이
루프의 품질 검증을 통과하면 자동 제출, 재시도 후에도 실패하면 사람
보류).

**보류(hold) 정책**: 재시도 2회를 다 써도 `verify_draft`를 통과 못 하면
자동 제출하지 않고 기존처럼 `status="unanswered"`로 남겨 사장님이
직접 처리하게 한다. 단, **백지 상태로 두지 않고, 검증에 실패한 마지막
초안을 "AI 추천 답글" 화면에 미리 채워서(prefill) 보여준다** — 사장님이
처음부터 쓰는 대신 그 초안을 고치게 하면 (a) 작업 부담이 줄고, (b)
"AI 시도 → 사장님 교정" 패턴이 더 자주 발생해 골든 예시 피드백 루프
(아래 4절, DeepTwin 순환 참고)가 더 빨리 돈다. 검증 실패한 초안을
버리지 않고 저장해둘 지점이 필요하다 — 정확한 스키마(어느 테이블/
컬럼)는 구현 단계에서 정한다.

**DeepTwin 순환과의 연결**: 보류된 리뷰를 사장님이 고쳐 써서
`save_final_reply`로 저장하면 → 자동으로 golden_example(판단사례)로
승격 → 불만 카테고리라 1.4절 "고신뢰 organic" 신호에 걸려 다음
비슷한 불만 리뷰에서 최우선 few-shot으로 쓰임 → store_style_profile
(원칙)도 자동 재생성 → 다음번 비슷한 리뷰의 초안 품질이 올라가 보류율이
자연히 낮아진다. 이 순환 구조 자체가 사실상 DeepTwin의 "기억→판단사례→
원칙→피드백" 패턴이다(아래 4절에서 "원칙" 레이어 고도화 + 이 순환이
실제로 작동하는지 측정하는 장치를 설계한다).

## 4. DeepTwin 원칙 증류

### 4.0 DeepTwin 개념 정리

DeepTwin은 기억/루프와 나란히 존재하는 별도 모듈이 아니다 — CoALA
기억(1절) + LangGraph 루프(2절)가 DeepTwin이 돌아가는 기반이고, DeepTwin
자체는 그 위에서 "기억 → 판단사례 → 원칙 → 사고절차"를 피드백으로
순환시켜 **진짜 사장님처럼 사고하는 것에 가까워지는 목표/성질**이다.
구체적 대응:
- 기억 = CoALA 전체
- 판단사례 = 일화기억(`golden_examples`)
- 원칙 = `store_style_profile`(아래 4.1절에서 고도화)
- 사고절차 = 2절의 LangGraph 루프
- 순환 = 2.1절 "보류→사장님 교정→golden_example 승격→원칙 재생성" 피드백

이미 설계한 메모리/루프가 "그릇"이고, **아직 진짜 새로 설계해야 하는
건 (a) 원칙 레이어의 고도화, (b) 이 순환이 실제로 작동하는지 측정하는
장치** 두 가지다.

### 4.1 원칙 레이어 고도화 — 카테고리별 판단 원칙 증류

**문제**: 지금 `store_style_profile`은 매장 전체에 톤 요약(5~7줄)
하나뿐이라 "배달지연 불만엔 이렇게, 맛 불만엔 저렇게"같은 **상황별
판단 패턴**을 담을 수 없다.

**설계**: `store_style_profile`을 매장당 1개가 아니라 **불만
카테고리별로 따로 증류**한다. 그 카테고리의 고신뢰 golden_examples
(1.4절)가 새로 쌓일 때마다 기존과 동일한 트리거(백그라운드 재생성)로
그 카테고리의 판단 원칙을 재요약한다 — 재생성 메커니즘 자체는 바꾸지
않고 카테고리 차원만 추가.

**사장님 확인 UI (훈련카드와는 다른 별개 장치)**:
- 훈련카드(OnboardingScenario) = 판단사례(원재료)를 새로 만드는 장치 —
  리뷰 부족한 카테고리에 가상 시나리오를 주고 답변 받음.
- 원칙 확인 = 이미 쌓인 사례에서 AI가 뽑아낸 요약이 맞는지 검수하는
  장치 — "AI가 파악한 배달지연 대응 원칙: ~~~"를 보여주고
  확인/수정받음.
- 데이터 흐름상 훈련카드(사례 수집) → 원칙 확인(그 사례의 요약 검증)
  순서로 이어지는 보완 관계, 대체 관계 아님.
- **비정기적·비차단**: 훈련카드처럼 매일 오는 게 아니라 그 카테고리
  원칙이 실제로 바뀔 때만 뜬다. 사장님 확인을 기다렸다가 적용하는
  게 아니라 새 원칙은 즉시 자동 적용되고(기존 store_style_profile
  자동 재생성과 동일), 확인 화면은 "여유 있을 때 검토, 틀리면 수정"하는
  선택 사항이다.

### 4.2 순환 측정 장치 (완료)

"지금 시스템이 사장님 진짜 판단에 얼마나 가까워지고 있나"를 추측이
아니라 대시보드에서 숫자로 확인하는 장치.

**측정 방법**: AI 초안과 사장님 최종본을 Voyage 임베딩(golden_examples
pgvector에 쓰던 것과 동일 인프라)으로 벡터화해 **코사인 유사도**를
계산한다. LLM-judge(LLM에게 "비슷한가요?" 물어보는 방식)는 쓰지 않는다
— 판단 편향 위험이 있고(AI가 AI를 판별), 순수 벡터 연산이 더 저렴하고
일관적이다. (1.4.1절의 임베딩 일관성 체크와 목적이 다르다 — 1.4.1은
"이 새 예시가 기존 신뢰 클러스터에 속하는가"를 golden_example 저장
시점에 거르는 필터이고, 이건 "AI 초안이 사장님 최종본에 얼마나
가까운가"를 저장 이후 대시보드에 보여주는 추세 지표다.)

**적용 범위**: AI 초안이 존재하고 사장님이 그걸 고치거나 다시 쓴
경우에만 계산 가능하다 — 1.3절 경로 A(보류→교정)와 경로 B(훈련카드,
`OnboardingScenario.draft_text`)가 대상이고, **경로 C(배민 직접 답글)는
애초에 비교할 초안이 없어 측정 대상이 아니다**(경로 C의 신뢰도는
1.4.1절의 임베딩 일관성 체크가 별도로 담당). 검증을 통과해 사람 개입
없이 자동 제출된 답글도 비교 대상이 없어 측정에서 빠진다 — "사람이
실제로 개입한 경우"만 신호로 쓰는 게 의도된 범위다.

**기록과 표시**: 이 유사도 점수를 그 리뷰의 생성 trace에 LangSmith
feedback으로 기록하고, `category`를 메타데이터로 함께 붙인다. 대시보드는
매장 전체 하나의 숫자가 아니라 **카테고리별로 따로** 추세를 보여준다
— 4.1절에서 원칙(store_style_profile)을 카테고리별로 쪼갰으니, 측정도
그 단위로 쪼개야 "배달지연은 수렴했는데 맛 불만은 아직" 같은 걸 구분해
볼 수 있다.

**향후 확장 지점(지금 범위 밖)**: 특정 카테고리 점수가 지속적으로
낮으면 그 카테고리의 훈련카드 노출을 우선시키는 식으로 연결할 수
있다 — 설계만 메모, 지금 구현 범위에는 안 넣는다.
